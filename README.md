# CS_360_Mobile_Architecture_Programming

### **Briefly summarize the requirements and goals of the app you developed. What user needs was this app designed to address?**

- I was tasked with developing an application that allowed a user to track inventory items for a warehouse/fulfillment center style. The client requested that the application required users to login to the service, and the users would then be able to perform several actions, such as view all available inventory, add new items to the company's inventory database, remove discontinued items from its database and ordering existing database items to the company's current stock. During this development, we created two database tables, one for users and the other for these inventory items, but they are within the same database. Unfortunately, the database must remain local for testing purposes and is not safe for production ready, as the database is not connected to a central cloud server, nor is it protected.
### **What screens and features were necessary to support user needs and produce a user-centered UI for the app? How did your UI designs keep users in mind? Why were your designs successful?**
- The main screens that were necessary were a login screen, that could double as registering an account page. In my case, I did separate pages for that, to keep my layouts clean. Other required pages involved showing the user the entire contents of the database for (in my case) company inventory, so I used a grid layout and an adapter that connects to this database and lists all the items sequentially in no particular order. I used one page for multiple separate activities (View Inventory / Remove Inventory / Order Inventory). Another required screen was adding a function for users to give permissions for SMS, which had some hidden elements as it awaited further permissions from the user before it showed all the layout elements.
### **How did you approach the process of coding your app? What techniques or strategies did you use? How could those techniques or strategies be applied in the future?**
- So before I developed the actual coding behind the application, I designed the UI layout so I could map out in my head which functions to work on first. I basically did all of the UI activity pages, and then went back and did one Java class starting from the first activity page and got it all polished and ready before moving on to the next one. One thing that I did not do and I regret doing was doing iterative testing. I did all of my coding, without testing often, and what resulted was all of my Java classes were destroyed. Turns out the Java classes were somehow created in the 'generated\' folder and during the build process, they were all wiped away. So moving forward, I will build out one activity page, and then write out its Java class.
### **How did you test to ensure your code was functional? Why is this process important, and what did it reveal?**
- For testing the application, I had to do all my testing the good old-fashioned way by interacting with the emulated device within the Android Studio IDE. While I could have done the UI testing methods, I never thought about doing it until after it was submitted. What this testing revealed is that there is often a lot of crashes that happen that aren't obvious to the developer, so I had several crashes and had to do some research to find out what the cause was, and fix it before I could move on to other tasks. Turns out one of the crashes happened because I did not put all the activity pages in the Manifest file. Something as simple as that can cause issues further down the line.
### **Consider the full app design and development process from initial planning to finalization. Where did you have to innovate to overcome a challenge?**
- I don't think that I did too much innovation here, but I did try following the preferred method of making all of your strings, and colors in their separate XML files and just calling their ids, rather than just hard-code each of the values. This makes it easier for the mobile application to use its translator API, although for testing locally, it serves no purpose other than clearing out warning messages through the IDE.
### **In what specific component of your mobile app were you particularly successful in demonstrating your knowledge, skills, and experience?**
- I think with the overall design, the design was very professional-looking, the color scheme was easy on the eyes and the overall UI was uncluttered and very descriptive. Any user new to this system would have no trouble navigating between screens, or have to squint to read any tiny text on the screen. I did add some sizing restrictions so if a user were to use a tablet versus a mobile phone, the buttons would still appear large, but not consume the entire screen space. I think another factor that I did very well was my handling of input validation, where I required that certain fields be non-null and accounted for that in several areas of the application, including account creation and adding a new item to the database.
